\section{Introduktion}

Gennem historien har der været benyttet mange forskellige billethåndteringssystemer, men
udviklingen kan overordnet inddeles i tre primære faser: den manuelle, den mekaniske og den
digitale.

Manuel bogføring var udgangspunktet for billethåndtering, hvor en medarbejder manuelt
registrerede de enkelte billetter. Senere blev der udviklet papirbaserede systemer, som gjorde
det muligt at standardisere udstedelsen og kontrollen af billetter.

Hulbaserede billetter var et væsentligt skridt mod mere strømlinet billethåndtering. Ved at
repræsentere information gennem huller i billetten blev det muligt for maskiner at aflæse og
behandle information efter fastlagte regler. Samme princip blev blandt andet anvendt i
stempelure, som oprindeligt registrerede arbejdstiden med et simpelt tidsstempel. For at
effektivisere den efterfølgende behandling begyndte man senere at benytte hulkort, hvor
arbejdstiden kunne registreres og efterfølgende maskinbehandles
~\cite{wikipedia_time_clock,wikipedia_punched_card}. Dermed kunne dele af håndteringen
automatiseres.

Digital billethåndtering repræsenterer den digitale fase, hvor billetter håndteres digitalt.
Det gør systemet markant mere dynamisk, da nye billettyper kan tilføjes, uden at der fysisk
skal ændres noget. Købet kan foretages før ankomst, og valideringen kan ligeledes foretages
digitalt. Rejsekortet er et eksempel på denne udvikling, hvor flere billettyper kan håndteres
af det samme system, og valideringen kan udføres ved at scanne kortet eller QR-koden i appen
~\cite{wikipedia_Rejsekort}.

\section{Kravspecifikation}

Formålet med kravspecifikationen er at konkretisere brugerhistorierne til funktionelle krav,
som efterfølgende kan verificeres gennem konkrete acceptkriterier.

\subsection{Brugerhistorier}

\begin{enumerate}
\item Som kunde ønsker jeg at kunne købe billetter inden ankomst, så jeg undgår kø ved
billetlugen.

\item Som kunde ønsker jeg at kunne betale online, så købet kan gennemføres hjemmefra.

\item Som kunde ønsker jeg at modtage mine billetter digitalt, så jeg nemt kan fremvise dem
ved ankomst.

\item Som kunde ønsker jeg at blive notificeret ved aflysninger eller ændringer i
afgangstidspunktet.

\item Som operatør ønsker jeg at kunne oprette og administrere afgange, så kunderne kan købe
billetter til dem.

\item Som operatør ønsker jeg at kunne administrere færger og deres kapacitet, så der ikke
sælges flere billetter, end færgen kan håndtere.

\item Som operatør ønsker jeg at kunne validere billetter, så jeg kan kontrollere dem ved
kundens ankomst.
\end{enumerate}

\section{Teknologi beskrivelse}

\subsection{Klient}

Klienten er udviklet i Elm, som er et funktionelt programmeringssprog til udvikling af
webapplikationer. Elm-kildekode kompileres til JavaScript, som efterfølgende afvikles i
brugerens browser. Klienten står for præsentationen af systemets data samt brugerens
interaktion med reservationssystemet og kommunikerer med API'et gennem HTTP.

\subsection{API}

API'et er udviklet med Flask, som er et webframework til Python. Flask håndterer
HTTP-forespørgsler fra klienten og eksponerer systemets funktionalitet gennem et REST API.
API'et fungerer som grænseflade mellem klienten og systemets data og står for behandling af
forespørgsler samt læsning og ændring af data i databasen.

\subsection{Server}

Nginx anvendes som webserver og reverse proxy. Webserveren leverer den kompilerede
Elm-klient til browseren, mens forespørgsler til API'et videresendes til Flask-serveren.
Dermed eksponeres klienten og API'et gennem samme webserver og origin. Nginx håndterer
desuden HTTPS-forbindelsen til klienten.

\subsection{Database}

SQLite3 anvendes som relationel database til persistent lagring af systemets data.
Databasen gemmes i en enkelt fil og tilgås direkte fra Python-serveren gennem SQLite3.
Datamodellen består af relationelle tabeller, som blandt andet repræsenterer brugere,
færger, afgange og billetter.

\subsection{Sikkerhed}

Let's Encrypt anvendes til at udstede TLS-certifikatet til webserveren. Let's Encrypt er en
certifikatudsteder, der tilbyder automatiseret udstedelse og fornyelse af TLS-certifikater.
Certifikatet gør det muligt at anvende HTTPS, så kommunikationen mellem klienten og
webserveren krypteres.

\subsection{Test}

Til enhedstest anvendes Pythons standardbibliotek unittest~\cite{unittest}.
Biblioteket indeholder funktionalitet til at definere og
strukturere testcases samt kontrollere forventede resultater gennem assertions. Testene kan
dermed afvikles direkte med Python uden yderligere testafhængigheder.

\subsection{Konfigurationsstyring}

GitHub anvendes til central opbevaring af projektets Git-repository. Platformen indeholder
projektets kildekode og versionshistorik og fungerer samtidig som udgangspunkt for
projektets CI/CD.

\subsection{CI/CD}

GitHub Actions anvendes til projektets CI/CD. GitHub Actions gør det muligt at definere
automatiserede workflows, som køres på baggrund af hændelser i projektets repository. I
projektet anvendes disse workflows til automatisk at køre tests samt bygge og publicere
projektets rapporter.
